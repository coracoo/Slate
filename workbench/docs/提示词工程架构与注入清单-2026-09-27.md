# Slate 提示词工程：注入清单与改造设计

状态：现状审计、目标设计及首轮实施记录。审计范围为 2026-09-27 工作区代码；项目运行时数据、厂商响应和实际生成质量未作线上验收。

## 首轮实施状态

- 已消除分镜、演员准备与表演提示词的系统补充重复注入；分镜检索经验只组装一次，设有回归测试。
- 编剧策略已拆为叙事结构、剧情节奏、连续性方法；分镜拆为镜头语言、关键帧方法、运动提示方法；图像把视觉画风与人物身份方法分开。旧项目 `style.json` 的单选保留为兼容入口，新维度可独立覆盖同维度旧选择。
- 自定义创作策略支持声明维度，保存时校验维度与目标；此处的 Markdown 策略仍是提示词片段，不是可执行 Agent Skill。
- 导入剧本拆集在项目保存了制作规格时读取目标集长；素材事实提炼不读取画风正文，画风仅在图像生成阶段应用。
- 项目文本模型调用在 `创作/提示词调用/` 留本地私有快照，记录阶段、模型、实际消息、基础参数、来源文件哈希与输入版本。内联图像不复制到快照，常见令牌打码；该目录不入 Git。当前已接剧本、分镜提示词优化、演员准备/表演、场景陈设和平面图生成。其他独立工具调用仍需逐一接线。
- `preproduction_flow.inspect_project` 将构想、设定锚定、分集、逐集正文、素材投影与分镜声明为只读阶段图，`/api/script/data` 返回状态，剧本页显示完成/可开始/待前置。导入剧本可跳过设定锚定；目前仅提供状态，不替代现有写入与校验器。
- 暂不引入 Claude Agent 作为写入中控。文本模型继续产出候选；阶段校验、版本和采用由工作台控制。跨模型质量、成本与稳定性对比留待有真实样本后执行。

完整提示词快照暂不通过 HTTP 展示：工作台监听地址可被局域网访问，未经认证的读取接口会暴露项目正文。可在本机项目目录查阅；若产品需要页面预览，应先设计授权与访问边界。

## 目标与边界

让「一句话构想 → 全剧骨架/世界设定 → 分集 → 分场剧本 → 素材投影 → S 转场镜头/V 分镜视频 → 媒体生成」各阶段有明确输入、输出、规则来源和版本记录。`storyboard.json` 仍是分镜与制作事实的唯一数据源；编剧上游数据继续按现有 `剧本/*.json` 与 `素材/*.json` 存储，不引入第二份可写的聚合圣经。画风不得改写剧情事实，导演手法不得覆盖镜头硬字段，检索知识不得冒充项目设定。模型负责创作和评审，工作台负责阶段顺序、校验、版本、落盘和副作用。

## 现有注入链路

| 阶段 | 当前主要入口 | 运行时文本来源与注入顺序 | 现状与风险 |
| --- | --- | --- | --- |
| 导入剧本拆集 | `creation_pipeline` → `prompt_modules.episodes_prompt` | 内置系统提示词 → `skills/system/episodes.md` 补充 → 原文 | 只做结构化拆集，不应引入画风。 |
| 一句话构想生成大纲 | `creation_pipeline` → `outline_prompt` | 内置格式/节奏/时长 + `brief.json` → 项目 `script` 选中正文 → `skills/system/outline.md` → 构想 | `outline_prompt` 内置短剧节奏，所选 Skill 可能写固定时长或不同结构；当前只有字符串拼接，没有约束冲突检查。 |
| 全剧最小单元 U1/U2 | `creation_pipeline` → `units_story_prompt` / `units_entity_prompt` | 内置 schema + 叙事/实体约束 → 检索知识 → 项目 `script` 正文 → 系统补充 → 构想、既有目录 | 这两项内部已经调用 `_emit`，未经过末尾通用包装。写入大纲、埋线、分集及人物/场景/道具档案后有确定性检查；检索案例的来源、适用范围应随调用记录。 |
| 逐集扩写 | `creation_pipeline` → `expand_episode_prompt` | 内置剧本格式 + `brief.json` + 项目 `script` 正文 + 已锚定设定 → 系统补充 → 本集卡/前情 | 已锚定设定是事实输入；「拆剧本 Skill」被文本称为节奏契约，但正文可包含超出节奏的指令。 |
| 素材提炼 | `creation_pipeline` → `characters/scenes/props_prompt` | 内置提取 schema + 既有目录/已锚定设定 → 系统补充 → 剧本文本 | 目前明确不在事实提炼阶段注入画风，方向正确。继续坚持「投影已有设定，不凭画风发现新实体」。 |
| 分镜 S 与 V 初稿 | `creation_pipeline` → `storyboard_prompt` + `production_prompts.CONTRACT` | 内置分镜契约 + 检索镜头经验 + 项目 `storyboard` 正文 + 已锚定设定 → 系统补充 → S 静帧/视频及 V 契约 → 剧本/资产索引 | 内置 `16:9`、`2–12s`、最多 `20` 镜等规则与项目规格/视频模型能力并非同一层；导演风格与视频提示词方法共用一个选项。系统补充存在重复注入，见下文。 |
| S/V 提示词重写、V 自动合并 | `production_jobs.llm_task` | `production_prompts.CONTRACT` + `EDIT_FORMAT`/任务规则 → 当前 `storyboard.json` 快照 | 单独使用 LLM 指令，不经过 `prompt_modules` 的系统补充与知识/Skill 装配；人工字段保护、镜号/时长校验已有。宫格是按需人工配置字段，虽然可单独按当前文本优化。 |
| 演员准备与表演 | `actor_pipeline` → `actor_prepare_prompt` / `actor_perform_prompt` | 内置角色知情/镜头锁定契约 + `acting` 正文 → 系统补充 → 分镜/角色状态 | 两个函数内部调用 `_emit`，又被通用包装器处理，系统补充也会重复注入。 |
| 拆片、台词归属、ASR 纠错、3D 陈设、故事版画格 | `analyze_film`、`attribute_speakers`、`fix_transcript`、`gen_scene_env`、`generate_panel_draft` | 各自内置契约 → `prompt_modules.sys_for` 追加同 ID 的系统补充 → 证据/上下文 | 与创作线另有接线，不能仅凭 Skill 中心预览判断实际运行效果。 |
| 资产设定图 | `gen_asset_images`/`chatgpt_queue` → `skill_lib.compose_asset_image_prompt` | 资产档案事实 → 资产级自由画风/资产 Skill/项目 `image` 三选一 → 资产类别硬约束与负面词 | 资产级自由文本优先于项目画风；这种覆盖需要明确显示来源。 |
| 镜头关键帧、视频提示词 | `create_batch`/`chatgpt_queue`/制作任务 → `prompt_compiler.compile_stage_prompt` → `prompt_assembler.assemble_shot_prompt` | S/V 作者文本 + 镜头结构字段 + `@` 资产引用 + 项目 `image` 正文 + 负面词；编译器另返回 stage `system_prompt` | 图像 Skill 也会进入视频的组装文本，媒介专用语可能串用。生成客户端主要消费拼好的 `content_prompt`；`system_prompt` 在批任务中作为元数据记录，不能假设每家图片/视频 API 都支持独立 system role。 |

关键文件：`workbench/tools/prompt_modules.py`、`prompt_compiler.py`、`prompt_assembler.py`、`production_prompts.py`、`production_jobs.py`、`skill_lib.py`、`story_units.py`、`creation_pipeline.py`、`workbench/skills/**`。选项落 `项目/剧本/style.json`；当前 `style_for(project,target)` 每个 `script/storyboard/image/acting` 槽位只返回一个正文。所谓本地「Skill」是带 frontmatter 的 Markdown 注入片段，尚不是能声明步骤、读写能力与验收条件的 Agent Skill 运行时。

## 已核实的结构问题

1. **系统补充重复注入。** `storyboard_prompt`、`actor_prepare_prompt`、`actor_perform_prompt` 函数内部已经 `_emit`，文件末尾 `_wrap` 再 `_emit`。用临时标记替换 `_override('storyboard')` 的只读验证结果为 `storyboard_override_count=2`。内置契约未丢，但自定义内容被重复强调；预览调用还可能与实际运行文本不同。
2. **知识与方法重叠。** `storyboard_prompt` 内已检索知识；通用包装器在有 `mood_text` 时再次检索并追加。一次调用可把同一镜头经验放两遍。
3. **一槽一文档，维度被挤占。** `three-act` 与 `shortdrama-hook` 共用 `script`；`motion-prompt` 与导演风格共用 `storyboard`。用户无法独立选择结构、节奏、镜头方法。`style.json` 的 `auto` 当前意为不注正文，并非模型自动挑选最适合的 Skill。
4. **绝对化风格会压制任务事实。** 例如 `cinematic-real` 中固定焦距/色调可与 S 镜明确指定的 24mm、光线相冲；`ghibli-soft` 含三视图相关语句，运行时靠 `skill_positive` 字符串过滤。这种过滤对文本改写脆弱，应从元数据上限制适用媒介和阶段。
5. **硬约束、偏好与建议混写。** 一次提示词里可能同时出现 `brief` 时长、短剧 Skill 的固定时长、分镜内置时长、视频模型档位。没有统一裁决机制；“末尾追加”“最高优先级”只是自然语言，不能替代结构化校验。
6. **流程 Skill 尚未建模。** `workbench/skills` 的正文直接注入模型；它不会驱动「先锁世界规则、再扩写、再提炼」的状态机，也没有阶段输入输出、失败回退、人工修改保护的机器可读定义。
7. **入口分散。** 剧本生成、S/V 优化、资产图、媒体编译、拆片各自拼文本。`transitions_prompt` 在注册表里可预览，但生产链未发现直接调用；需要标成预留功能，不能在 UI 表示为已自动执行。

## 目标分层与裁决规则

| 层 | 内容 | 权限与存储 |
| --- | --- | --- |
| L0 项目事实 | 用户构想、`brief.json`、已锚定大纲/埋线/素材、现行 `storyboard.json`、人工编辑 | 最高事实权威。下游只能引用或提出变更，不能静默覆写。 |
| L1 系统硬契约 | 阶段 schema、可用 ID、输出格式、禁止凭空建实体、镜头/台词锁定、API 能力限制 | 代码与校验器持有，版本化；用户可在产品字段中改变业务参数，但自由文本不能把契约改掉。 |
| L2 流程方法 | 编剧拆解顺序、连续性复核、导演分析、素材投影、阶段验收与重试 | 机器可读的工作流 Skill，负责调用已有函数与确定性 gate；不充当画风正文。 |
| L3 创作偏好 | 叙事结构、节奏、类型、导演镜头语言、视觉媒介、表演手法，各维独立选取 | 有适用阶段/媒介、强弱、版本与冲突声明；只能在 L0/L1 边界内影响表达。 |
| L4 检索证据 | 拉片知识卡、用户经验、参考片例 | 带来源、相关镜头、命中理由；默认是建议而非项目设定。一次阶段只注一次，限量去重。 |
| L5 本次任务 | 当前集/场/S/V、人工提示词、参考资产、负面词 | 使用结构化槽位传递；人工文本改动保留来源标志和 revision。 |
| L6 厂商适配 | 支持的画幅、时长、首尾帧、参考图数、negative 字段、语音/镜头语法 | 生成前按具体模型生成参数与媒体提示词；不反写剧情源数据。 |

冲突按 **L0 事实与用户显式制作规格 → L1 有效性 → L2 阶段职责 → L3 偏好 → L4 参考案例** 裁决；L6 只决定本次请求可否执行及如何转译。两项同层且互斥时展示冲突并让用户选择，不让模型在长提示词里自行猜。例：`24mm` 镜头事实压过画风片段的 `85mm`；模型只支持 5 秒视频时，不能偷偷把用户的 3 秒 S 改成 5 秒，应由 V 合并或显式改时长。

建议将 `script` 拆为 `structure`、`pacing`、`dialogue`、`continuity`；`storyboard` 拆为 `blocking`、`camera_language`、`editing_rhythm`；`image` 拆为 `visual_style` 与 `asset_sheet`，另为视频设 `video_motion`。不是把各维度原文无条件拼成一个更大的 system prompt：阶段只选择适用片段，每一维可多选时必须有冲突规则与长度预算。

## 建议的流程与 Agent 边界

保留工作台作为确定性中控：阶段 DAG、任务幂等、输入快照、模型选择、校验、版本、失败重试、成本记录和用户审核由应用代码执行。LLM（可选 Claude、MiniMax、豆包等）继续生成一句话扩展、剧本、大纲、世界设定、分集、分镜以及局部重写；它们返回候选结构化结果，不直接写最终项目文件。先使用同一接口让不同文本模型跑相同的阶段任务，比较质量、JSON 有效率、连续性、成本与耗时，再决定是否新增专用 Agent 控制层。

Claude Agent 或其他 Agent 适合**可选的前期策划/复核助手**：读取经过授权的项目快照，提出分段、冲突、角色动机与缺口建议，调用只读查询或受控草稿工具；每个步骤的最终写入仍经工作台校验和版本快照。不要把项目事实、任务状态和外部 API 调用权全部交给一个自由循环的 Agent。把画风生成和视频生成接在 L6 媒体层即可，前期编剧 Agent 不需要掌管它们。

建议阶段图：`构想 + brief → 全剧骨架与规则/埋线/人物名册（锚定）→ 分集卡 → 逐集分场剧本 → 素材事实投影 → S 分镜及两类作者提示词 → V 编排 → 图片/视频适配与生成`。每阶段保留 `输入 revision → 提示词构件版本 → 模型/参数 → 候选输出 → 校验 → 审核/采用 → 输出 revision`。生成输出不通过 gate 时保留草稿与失败原因，不越级写下一阶段。

## 实施顺序与验收

1. **P0 修接线与可观测性。** 消除 `_emit` 双调用和重复知识注入；列出每个注册提示词的真实调用方；将未接线的转场项标注为预留；增加按任务查看「最终发送文本/各段来源/版本/模型」的脱敏预览。先锁住当前结果的回归测试。
2. **P1 建统一编译产物。** 用 `PromptBundle` 保存 `stage`、输入 revision、硬契约版本、选中方法及 hash、事实引用、检索来源、作者文本、输出 schema、模型能力、最终发送内容与负面词。所有 LLM 与媒体调用记录同一结构；不要求所有厂商 API 真有 system role。
3. **P2 拆多维策略与冲突检查。** 迁移旧 `style.json` 单选值，保持旧项目画面不变；对冲突给具体字段与来源，不用追加“最高优先级”口号。给资产设定图/单镜静帧/视频分别设适用范围。
4. **P3 固化前期工作流。** 将现有 U1/U2、扩写、投影、分镜的状态转移、校验与人工保护声明为流程 Skill；先跑同一项目的旧/新产物对比，再逐阶段替换。
5. **P4 试验 Agent。** 选两个规模不同的剧本，对比「现有 LLM 分阶段」「Claude 作策划/复核，Slate 控制落盘」；以有效率、跨集一致性、返工次数、成本/时长判断是否长期启用。未达到指标则保持 LLM 分阶段链路。

验收至少覆盖：项目画幅与镜头焦距不被风格覆盖；用户人工改动与已锚定实体不被重写；系统补充、知识卡各注入一次；不同阶段只读其适用 Skill；`prompt_image` 与 `prompt_video` 不混用；一次请求可复原 PromptBundle 与最终发送内容；未通过 schema/连续性检查不落正式文件。
